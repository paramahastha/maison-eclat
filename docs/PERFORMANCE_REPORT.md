# Performance report

Wet inspector follow-up (2026-11-07): the original drop/rings were replaced with a demand-rendered 3D wave surface and instanced glass beads. A headed Chromium development sample on this Mac measured 119.96 rendered frames/s over 6.5s and zero frames over 600ms while offscreen (`docs/screenshots/wet-study/lab-dev.json`). Intersection and document-visibility listeners pause animation; reduced motion defaults to a static poster. This is a local unthrottled development sample, not production field CWV or a physical phone benchmark.

Latest scroll upgrade (2026-11-07): [current validation and visual evidence](motion-upgrade/QA_REPORT.md). The results below document the preceding baseline.

Date: 2026-11-07 (Asia/Jakarta). Local **production build**, visible Chromium using **ANGLE Metal / Apple M4**, browser viewport DPR 1, application DPR capped at 1.5 desktop / 1 mobile. Raw final sample: `docs/performance-lab.json`. These are short local lab samples on a warm server, not field CWV, p75 statistics, a Lighthouse score, or a real mobile-device benchmark.

Desktop: 1440×900, unthrottled local connection. Constrained mobile simulation: 375×812, DPR 1, 4× CPU slowdown, 100 ms network latency, 1.6 Mbps download / 750 Kbps upload. The simulated mobile profile still uses the M4 GPU, so its frame rate is **not** an estimate of a physical phone GPU. Each scroll sample lasts about four seconds; OS/background activity is not controlled. The display delivered roughly 120 animation frames/s; actual WebGL draw callbacks are counted rather than treating requestAnimationFrame alone as rendered output.

Interaction values come from Event Timing entries with a nonzero interaction ID during menu open/close and fragrance selection. They are a small-sample lab responsiveness signal, **not field INP**. No real-user p75 LCP/INP/CLS data exists. Neither profile reported an uncaught page exception. The small mobile layout shift occurred during initial loading and remains well below 0.1 in this sample.

## Delivery and rendering budget

- Original GLB: **234,436 bytes / 228.9 KiB**, below the plan's approximate 1.5 MB target. All required separate parts validated.
- Delivered WebP posters: about **39–41 KiB each**, with Next responsive image sizing. Source PNGs and the editable .blend are not downloaded by the site.
- Observed encoded JavaScript resource bytes after the scene loaded: **473.3 KiB** across ten chunks in the local sample. This includes the deferred 3D chunk; it is not a statement that all those bytes block first paint.
- Self-hosted fonts, original local label textures, generated lighting; no remote HDRI, decoder, video, Lenis, postprocessing or second home canvas.
- Demand rendering invalidates on scroll, variant/material changes and product rotation. Ref interpolation settles without per-frame React state. Mobile uses DPR 1 and a smaller environment capture.
- Asset inventory: `docs/asset-budget.json`, generated by `npm run assets:validate`.

## Diagnostic runs and limits

The first headless run used **SwiftShader software rendering**, with roughly 4.6 fps desktop and 15.3 fps in the smaller constrained viewport. It is retained as `docs/performance-software-renderer.json`; it is not the M4 hardware result. Browsers using software WebGL may perform poorly. Reduced-motion/static artwork and model/context-failure fallbacks remain available, and no software-rendering performance guarantee is made.

An early M4 diagnostic is retained in `docs/performance-m4-initial.json`. Its raw maximum Event Timing values included non-interaction pointer events and should not be compared to field INP; the final script filters nonzero interaction IDs. The final run also verifies responsiveness after adding explicit invalidation for material changes.

The current stable R3F version emits a nonfatal Three.js Clock deprecation warning with Three 0.185. It is not a shader failure or uncaught exception; no warning suppression or alpha-library upgrade was used. See `docs/browser-console.json`.

## Reproduce

With a production server on port 3001:

```sh
npm run build
npm run start -- --hostname 127.0.0.1 --port 3001
# In another terminal:
BASE_URL=http://127.0.0.1:3001 PRODUCTION=1 HEADLESS=false node scripts/measure-performance.mjs
npm run assets:validate
```

Use a visible hardware-accelerated browser when comparing GPU results. Repeat on actual target phones and collect real-user metrics only if a later authorized deployment introduces measurement.
